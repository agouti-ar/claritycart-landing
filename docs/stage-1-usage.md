- api/chat.js и server.js используют общий обработчик. При отсутствии локального AI key прокси передаёт запрос production API без локальной записи; старый API без нового протокола не считается успешной записью.

## Семантика

- Новый осознанно отправленный вопрос получает новый ID, даже если текст совпадает с ранее успешно отвеченным.
- Повтор доставки того же ID не генерирует новый ответ и не добавляет вторую строку questions.
- Успех возвращается после commit: одна строка questions на успешный request_id; вопросы с ошибкой/blocked/quota не расходуют usage.
- После потери подтверждения commit повтор возвращает сохранённый результат.
- Одновременная доставка незавершённого ID получает REQUEST_PENDING. Клиент повторяет тот же ID.
- После аварийного завершения процесса processing старше двух минут при повторе становится REQUEST_EXPIRED, без расхода. Пользователь затем может сделать новый запрос. Старый процесс уже не сможет записать usage поверх этого результата.
- Это не обещание exactly-once выполнения у внешнего AI provider: при аварии провайдер мог выполнить запрос, но наш сервер не получил/не сохранил результат. Это гарантия отсутствия повторного учёта одного ID на нашей стороне.
- Разные request_id пока могут одновременно пройти старую проверку квоты. Атомарное резервирование общего лимита — этап 2.

## Миграция — подготовлена, НЕ применена к Supabase

Последствия:
1. Добавляются chat_requests и две RPC-функции. Старые вопросы не удаляются и не переписываются.
2. Добавляется хранение результата AI для безопасного replay. Таблица закрыта от anon/authenticated; RPC разрешены service_role.
3. Отзывается INSERT в questions у PUBLIC/anon/authenticated. Старые браузеры больше не смогут писать usage напрямую. SELECT/RLS для чтения существующего dashboard не меняются.
4. Для этой операции нужна согласованная выкладка API и виджета. Нельзя применить миграцию отдельно к старому production и считать обновление завершённым.
5. Без RPC новый API возвращает 503 и не вызывает AI — резервной небезопасной записи нет.

Перед применением на отдельном тестовом Supabase нужно проверить реальную схему questions (id defaults, обязательные поля, триггеры, grants/RLS). В репозитории этих определений нет. Локальный SQL-тест проверяет совместимую минимальную схему, а не конфигурацию живого проекта.

Нужны SUPABASE_URL, SUPABASE_SERVICE_KEY на сервере и GEMINI_API_KEY для AI. Не помещать service key в frontend. Для local proxy remote deployment должен уже поддерживать request_id/usageRecorded. В Vercel проверить допустимую длительность функции: бюджет AI 25 секунд + DB RPC до 8 секунд каждый; нужен запас не менее 45 секунд (предпочтительно 60, если доступно).

Порядок проверки: согласование миграции → test Supabase/schema review → миграция → preview API + widget одной версии → реальный AI запрос → replay → blocked/quota → сверка questions и кабинета. Production — отдельное согласование после preview.

Не удалять журнал request_id произвольно: без политики срока принятия старых запросов очистка может снова разрешить повтор старого ID. Retention и privacy потребуют согласования на этапе 11.
